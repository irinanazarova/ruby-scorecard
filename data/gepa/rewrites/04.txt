This guide explains the let_it_be recipe from TestProf, a Ruby toolkit for profiling and speeding up test suites, and shows how it helps you set up shared test data with very little effort. Many automated tests need example records in the database before they can run. In the RSpec testing framework, the usual way to create such records is with the let and let! helpers, which define a named value for each test. The trouble is that let! recreates its records before every single example, so a group of twenty tests that all rely on the same four records will build those four records twenty times over. For test suites that touch a real database, this repeated setup is one of the most common reasons tests run slowly.

To understand let_it_be, it helps to first understand before_all, another TestProf feature. The before_all helper runs a block once for an entire group of related tests rather than once per test, wrapping the whole group in a database transaction that is rolled back afterward. This makes the setup data repeatable across examples while creating it only one time. The drawback is that before_all forces you to assign your records to instance variables and to define them all together in a single block, which makes it awkward to adopt in existing tests that already use let and let!.

The let_it_be helper combines the convenience of let with the efficiency of before_all. You write let_it_be exactly as you would write let!, giving each record a name and a block that creates it, but the record is created only once for the surrounding group of tests instead of once per example. In practice, converting a slow test file can be as simple as replacing each let! with let_it_be. One important detail follows from this design: let_it_be restores the database between groups of tests but not between individual examples within a group. You therefore still need a mechanism that wraps each example in its own transaction and rolls it back, such as transactional fixtures in RSpec Rails, the DatabaseCleaner gem, or equivalent custom setup, so that one test does not leak data into the next.
