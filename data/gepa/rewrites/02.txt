This section explains how to build a custom base policy in Action Policy, a Ruby authorization library, so that you understand what a policy class is composed of and how to replace the default building blocks. In Action Policy, a policy is an ordinary Ruby class that holds the rules deciding whether a given user is permitted to perform a particular action on a particular record. Each rule is a predicate method, a method whose name ends in a question mark and that returns true or false. Applications conventionally place these rules in a shared parent class named ApplicationPolicy, from which all individual policies inherit.

By default, that parent class inherits from ActionPolicy::Base, which is a ready-made combination of every available policy extension assembled with sensible default configuration. ActionPolicy::Base brings together a set of modules, each contributing one capability: a core module that performs the actual authorization checks, along with separate modules that add pre-checks, human-readable failure reasons, rule aliases, scoping of collections, caching of results, and a set of default rules. When used with Ruby on Rails, it also registers scope matchers for ActiveRecord relations and for controller parameters, and it enables instrumentation through Active Support notifications. The defaults it supplies include treating the current user as the authorization subject, using a general manage? rule as the fallback, aliasing the new? action to create?, and denying the index?, create?, and manage? actions unless you override them.

You are not required to inherit from this fully featured base. If the bundled defaults do not fit your needs, you can write ApplicationPolicy from scratch and include only the pieces you actually want. The single indispensable component is the core module, ActionPolicy::Policy::Core, which provides the fundamental apply and allowed_to? methods that every policy relies on to evaluate rules. A minimal policy therefore needs nothing more than that one module included in your class.

One caveat applies when working with Rails: the custom scope matchers that let policies filter ActiveRecord relations and controller parameters are normally registered inside ActionPolicy::Base. If you build your own base instead, you must copy that setup code yourself in order to keep using those matchers.
