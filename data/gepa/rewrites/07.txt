This tutorial teaches you how to build a GraphQL application using Ruby on Rails on the backend and React with Apollo on the frontend, starting from nothing and finishing with your first working query. By the end you will understand what GraphQL is, why developers reach for it, and where it can lead you astray, so that you can decide whether it suits your own project rather than adopting it simply because it is popular. GraphQL appears everywhere now, but there is no silver bullet, and it is worth understanding both its advantages and its trade-offs before shifting an existing application away from REST.

GraphQL is, according to its specification, both a query language and a runtime, also called an execution engine. A query language is a way of describing how a client communicates with an information system: it defines the form of the requests a client can make. The runtime is the part responsible for fulfilling those requests by gathering and returning the actual data. At the heart of every GraphQL application sits a schema, which describes the underlying data as a directed graph, meaning a set of types connected by relationships. The runtime must answer queries according to this schema, so any valid GraphQL server processes the same query against the same schema in the same way and returns data in the same format. In effect, the schema is everything a client needs to know about the API.

A query selects a portion of that schema. It names the fields it wants, starting from a root field, and may pass arguments such as an identifier to locate a specific record. Because a query mirrors a sub-graph of the schema, a client can request exactly the data it needs, no more and no less, in a single round trip. This directly addresses overfetching, a common frustration with traditional REST APIs where endpoints often return more information than the caller wants. GraphQL schemas are also strongly typed, which means both the client and the runtime can verify that the data exchanged matches the declared types, catching mistakes early and making the contract between frontend and backend explicit and reliable.
