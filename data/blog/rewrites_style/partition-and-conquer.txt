There is a moment in the life of a growing application when a single database table stops being a convenience and quietly becomes the thing that wakes your on-call engineer at three in the morning, and this is a tale of database partitioning drawn from exactly that kind of real event.

Table partitioning is the technique of taking one enormous table and splitting it into a number of smaller physical tables, called partitions, that the database still presents and queries as though they were a single logical table. PostgreSQL is the open-source relational database we are working in here, and it can route an incoming query to only the partitions that could possibly hold the requested rows, so a search that once had to scan millions of records can touch a small slice of them instead. A database index is a separate sorted structure that lets the engine jump straight to the matching rows without reading the whole table, and on our orders data we build an index on the country and scheduled_at columns together, because the queries we run most often filter on exactly those two fields.

Query performance is simply how long the database takes to return the rows that a request asks for, and it is the number that decays first and most visibly as a table grows, because the cost of scanning rows and of keeping an index balanced both climb steadily with the row count. We learned this the hard way: one of our clients, Gett, had an orders table that swelled over time to several million rows, until some of its most common queries took hours rather than milliseconds to finish. Each order carries a country code, an order type, a scheduled timestamp, a cost, and a JSON blob of extra data, and the three operations that matter are fetching one order by its id, listing every order from a given country within a time window accurate to the minute, and updating an order's cost or attached data.

Rails is the Ruby web framework whose ActiveRecord layer maps each database row to a Ruby object, and it is the application that ultimately has to read and write these orders without ever noticing that one table quietly became many. Dividing a live, several-million-row table while production traffic keeps flowing is a standard technique that nonetheless demands real caution, and this guide works through it hands-on, first generating a thirty-million-row table of fake orders to recreate the problem honestly, then taking it apart with PostgreSQL so that nothing is lost in transition.
