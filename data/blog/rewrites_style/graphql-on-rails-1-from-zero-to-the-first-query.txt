There is no silver bullet, and GraphQL is no exception, so this guide explains what GraphQL actually is and where it pays off before you rewrite anything. GraphQL is a query language and a runtime for fulfilling those queries with your existing data, two ideas that are worth pulling apart before the hype pushes you to swap REST for it across an entire application. A query language, by definition, describes how a client communicates with an information system, so it gives the frontend a precise way to ask for exactly the fields it wants. A runtime, also called an execution engine, is the part on the server that receives a query and resolves it into real data. Because the language and the runtime are defined separately by the specification, every valid GraphQL server runs queries the same way and returns data in the same format.

At the core of every GraphQL application lies a schema, which describes the underlying data as a directed graph and tells the runtime how each piece of data connects to the others. The schema is everything clients need to know about the API, because the runtime must execute every query according to it and to the general rules from the specification. A type, the schema's basic building block, names a kind of object such as a product or a manufacturer and lists the fields that object exposes, like its id, its title, or its related records. Because GraphQL schemas are strongly typed, both the client and the runtime can confirm that the data passed across the boundary is valid before a single record is touched.

This design gives GraphQL its first real benefit over traditional REST APIs. A query represents a sub-graph of the schema, so a client can fetch only the data it needs, and all of it, in a single request, which removes the overfetching that REST endpoints suffer when they return fixed payloads. In this multi-part tutorial we build a real application around that idea, using the graphql-ruby gem, the standard library for defining schemas and resolving queries in Ruby, on a Rails backend, paired with React and Apollo on the frontend. We will cover the advantages honestly alongside the caveats and pitfalls, and the ways to deal with them.
