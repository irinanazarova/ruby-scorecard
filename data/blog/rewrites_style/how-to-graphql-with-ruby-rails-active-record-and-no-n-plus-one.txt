GraphQL is a query language for application programming interfaces, or APIs, that lets a client request exactly the data it needs in a single round trip, where an API is the contract through which a server, written in Ruby, translates incoming HTTP requests into SQL database statements with the help of an object-relational mapper. You switched a mature Rails backend from REST to GraphQL to streamline your endpoints, and now your database is unhappy with all the extra queries this flexibility produces. This guide explains why that happens, and it shows the tools that let a Ruby application solve the N+1 problem without trading one performance cost for a worse one.

Unlike a traditional REST design, which exposes many fixed endpoints that each return a predetermined shape of data, GraphQL gives every client, whether a frontend framework or another service, a single endpoint for fetching data in any shape and size it requires. That flexibility is the reason teams adopt it, and it is also the source of one important catch that concerns how the database gets queried underneath each request.

The N+1 query problem describes the situation in which loading a list of parent records issues one query to fetch the parents and then one additional query for each parent's associated records, so a feed of one hundred tweets quietly executes one hundred and one separate queries instead of a small handful. This problem is especially difficult to avoid in GraphQL because the set of associations to load is determined at runtime by whatever the client happens to request, which leaves the server very little opportunity to plan its database access ahead of time. A team therefore faces a choice between accepting one query per parent plus one query per association, or fetching every association the client might possibly ask for in advance.

Preloading, also called eager loading, is the ActiveRecord technique of fetching a record together with its associated records up front in a few larger SQL statements rather than lazily, one association at a time. ActiveRecord is the object-relational mapper bundled with Ruby on Rails that maps rows in a relational database to Ruby objects and back, and it is the layer responsible for all of this loading. The genuine tradeoff is that when an application has the rich, deeply connected schema that motivated the move to GraphQL in the first place, blanket preloading can strain the database even more heavily than the N+1 pattern it replaces, because it loads associations that no client actually requested. The way through is to stay selective and load only what each resolved query truly needs, exactly when it needs it, and nothing more.
