This guide explains how to build a GraphQL API in a Ruby on Rails application that fetches data efficiently, without falling into the notorious N+1 query problem that GraphQL tends to provoke. GraphQL is a query language for APIs that lets clients ask for exactly the data they need in a single request, and it can do wonders in a backend-only Rails application by giving consumers, whether a frontend framework or another API, one flexible endpoint for fetching data in whatever shapes and sizes they require. There is only one catch, but it is a big one, and it is N+1 big.

The difficulty arises because the list of associations a GraphQL query needs to load is always determined at runtime, which makes it very hard to be smart about querying the database ahead of time. You are left with two unappealing options. You can either accept the reality of running one query for the parent record plus one additional query for each associated record (which is why people call it N+1, even though the stricter term would be 1+N), or you can try to load every possible association in advance with elaborate SQL statements. The trouble is that if you have a rich schema, and a rich schema is usually the very reason teams switch to GraphQL in the first place, aggressive preloading can place an even heavier strain on the database than letting N+1 queries run unchecked. Fortunately, the Ruby and GraphQL ecosystem offers tools that let us be far more selective and intelligent about what we load, as well as when and how we load it.

To keep the discussion grounded rather than abstract, this article works through a practical example built around a deliberately simple schema for a small Twitter clone application. The schema centers on three types that should feel immediately familiar: Tweet, User, and Viewer. The Viewer represents the user who is currently looking at the feed of other users' tweets, and it exists as a separate type from User because a current user may expose properties that are not accessible on a general user. With this example in place, the article goes on to compare several different optimization methods, backed by a runnable set of specs, so you can see precisely how each approach affects the number and cost of the queries your database has to perform.
