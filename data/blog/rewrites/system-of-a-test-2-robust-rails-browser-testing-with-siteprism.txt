This guide explains how to write robust Rails browser tests using SitePrism, a Ruby library that wraps each page of your application in a reusable page object so that your Capybara test code no longer depends on the raw HTML markup. The core problem it solves is a familiar one: Rails system tests that turn red every time someone makes a minor change to the application's frontend, even when that change has no effect on what a user actually sees or does. By abstracting page implementation details behind page objects, SitePrism makes the testing code more generic and far less brittle. This is the second part of our series on system testing in Rails, and it draws on real techniques refined during Evil Martians' commercial work.

The first part of the series concentrated entirely on setting up the environment for browser tests in Rails, using Ferrum, Cuprite, and Docker, without showing a single actual test or scenario. That was a deliberate choice, partly because a single article can only cover so much, and partly because there are already many excellent community resources for anyone learning the basics of end-to-end testing with Capybara. This installment skips those fundamentals and moves on to more advanced techniques for organizing and DRYing out your browser testing code, covering an introduction to SitePrism, the configuration of test identifiers in Capybara, and a bonus approach for keeping test IDs from leaking into production markup when using Slim.

Browser tests have grown steadily more popular since Rails bundled them in as system tests, yet many developers still avoid them because they run slowly and cost a lot to maintain over time. Little can be done about the speed, since browser tests will never match the pace of unit tests, but that is a compromise worth accepting because unit tests cannot exercise the real end-user experience at all. Maintainability, however, is something you can genuinely improve. The complaint engineers most often raise against end-to-end tests is that changes to HTML markup break the build and force them to refactor their tests far too frequently, which holds true for most suites in the wild: a change to HTML, CSS, or JavaScript can make tests fail even when it leaves the user experience untouched. The remainder of this post shows how page objects break that fragile coupling and keep your system tests green through ordinary frontend churn.
