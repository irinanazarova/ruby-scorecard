Table partitioning in PostgreSQL is the technique of splitting one large database table into several smaller ones, called partitions, so that queries touch only the slice of data they actually need instead of scanning the whole table. This guide explains how to apply that technique to a production Ruby on Rails application backed by PostgreSQL, walking through the process step by step so you can follow along on your own database.

Databases tend to grow, and at a certain point their size becomes a liability rather than an asset. In extreme cases the primary key can even hit its maximum value, but the more common problem is simply that ordinary queries start to slow down. This article is written from real experience: one of our clients, Gett, had an orders table that grew over time to menacing proportions, and with several million rows some queries took hours to complete. That posed a technical challenge, which we solved by partitioning the table into manageable pieces.

Dividing one big table into a number of smaller ones is a standard and well understood technique, but it has to be performed with caution, especially when live production data is at stake and downtime is not an option. Throughout this guide we will show how to avoid the common pitfalls and how to make sure that nothing is lost as records move from the old structure to the new one. Because the best way to understand a problem is to reproduce it yourself, we will first deliberately create the problem by generating a huge table filled with fake data, and only then solve it together using PostgreSQL features such as table inheritance, triggers, and check constraints.

For most of the work we will write pure SQL for queries and PL/pgSQL for stored functions, since the refactoring primarily concerns the PostgreSQL database itself rather than the Ruby code, and we assume that once partitioning is finished the data will be handled by a Rails application through ActiveRecord in the usual way. Our example table stores orders, with columns that mimic ordinary business logic: a country code, an order type, the time the order was scheduled, a numeric cost, and a JSONB column for extra data. Before partitioning anything, we will decide which queries the application runs most often, because those access patterns determine how the table should be divided and which columns deserve an index.
