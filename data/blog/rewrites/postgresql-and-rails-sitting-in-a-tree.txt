This guide explains how to store hierarchical tree data in PostgreSQL from a Rails application, and it argues that the Closure Table pattern is the best-designed of the common approaches because of how cleanly it models parent-child relationships. A tree, in this context, is data where every record points to a parent, so that regions contain cities, cities contain streets, and streets contain individual houses, all the way down from a single root node to the leaves at the bottom.

The lessons here come from a real project whose goal was to systematize a sprawl of disorganized databases, the hardest of which were the toponym databases that described geographic place names. The source data arrived as a deep XML tree with more than a million unsorted records, each one carrying an id, an optional parent id, and a name, so that the Kremlin pointed at Moscow, Red Square also pointed at Moscow, and Moscow itself sat near the top with no parent above it. The job was to load this entire tree into PostgreSQL so that it could be queried efficiently.

A typical query needed to fetch every street belonging to the cities within a given region, or to walk the whole path from a single street at the bottom up to the root node above it. Because the application had to run many such queries, each one had to return as fast as possible, which is why a dedicated hierarchical storage pattern was necessary to speed them up. That requirement shaped the three stages of the work: importing the raw table, choosing a suitable hierarchical pattern, and calculating the extra reference data that the chosen pattern depends on. At every stage, speed was the deciding factor, since an unresponsive server and the downtime that comes with it are among the worst outcomes a project like this can produce.

The first stage, importing the initial data, is best handled in PostgreSQL by the COPY FROM statement, which populates a table significantly faster than a long series of individual INSERT statements. COPY FROM accepts its input as either CSV or a binary file, and the binary form is the faster of the two, so the import pipeline converts the records into PostgreSQL's binary format before loading them in a single bulk operation.
