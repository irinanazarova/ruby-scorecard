In this article you will learn how to use table partitioning in PostgreSQL to break down a single gigantic database table that has grown large enough to slow a production application down to an unacceptable degree. Table partitioning is the technique of dividing one large logical table into a collection of smaller physical tables, called partitions, so that the database can store and search each piece independently while the application continues to treat them as though they were a single table. PostgreSQL, the open-source relational database system on which this guide is based, organizes data into tables made up of rows and columns and lets you attach indexes and functions that change how that data is stored and retrieved. A database index is an auxiliary data structure that the database maintains alongside a table so that it can locate the rows matching a query without scanning every row, which is the central reason indexes improve query performance. Query performance, meaning the speed with which the database returns the rows that a request asks for, matters because a query that takes hours instead of milliseconds can make an otherwise healthy application unusable.

By the end of this walkthrough you will understand why a table can grow into a liability, how partitioning addresses that problem, and how to carry the change out safely on a system that holds live data. The lesson is drawn from real experience, because one of our clients operated an orders table that grew over time to several million rows, at which point some queries took hours to complete and the table became a genuine technical obstacle rather than a mere inconvenience. Because dividing a large table is a standard but delicate operation that can lose or corrupt data when performed carelessly, we will move carefully and point out the common pitfalls that cause data to be lost in transition.

Since the best way to learn a database technique is to practice it on data you can freely destroy, we will first manufacture the problem by generating a huge table filled with fake orders, and only then solve it together using the partitioning features that PostgreSQL provides. We assume throughout that once the database work is finished, the data will ultimately be read and written by a Ruby on Rails application through ActiveRecord, the object-relational mapping layer that lets Rails treat database rows as ordinary Ruby objects.
