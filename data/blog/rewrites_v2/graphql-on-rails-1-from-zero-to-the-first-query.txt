In this opening part of a multi-part tutorial you will learn what GraphQL is, how it organizes the communication between a client and a server, and how the technology fits together with a Ruby on Rails backend so that you can build up to writing and understanding your very first query. Before introducing any code, it helps to define the central terms carefully, because much of the confusion around this technology comes from using its vocabulary loosely. GraphQL is a query language and runtime, which means it is both a formal notation that describes how a client should ask an information system for data and an execution engine that is responsible for fulfilling those requests by gathering and returning the data they describe. A query language, by definition, is a structured way of expressing exactly what information you want to retrieve from a system, so that requests are unambiguous and can be validated before they run. At the core of every GraphQL application lies a schema, which is a description of the underlying data expressed as a directed graph and which acts as the single source of truth that clients rely on to understand everything the API can offer. Because the runtime must execute every request strictly according to this schema, any valid GraphQL server will run the same request in the same manner and return data in the same format, which is what makes the behavior of these systems so predictable across implementations. A type is one of the building blocks of that schema, and because GraphQL schemas are strongly typed, both the client and the runtime can verify that the data being passed is valid, catching many mistakes early rather than at runtime. You will also see how these ideas connect to Ruby on Rails, which is a popular web application framework written in the Ruby programming language that handles the server-side logic of an application, and to the graphql-ruby gem, which is the library that lets a Rails backend define its schema and execute incoming queries. Understanding why these pieces matter is important, because GraphQL lets a client fetch exactly the data it needs, and no more, in a single request, which directly addresses overfetching, a common shortcoming of traditional REST APIs where responses often contain far more information than any one screen actually uses. By the end of this introduction you will be ready to read a real query and recognize each of its parts with confidence.
