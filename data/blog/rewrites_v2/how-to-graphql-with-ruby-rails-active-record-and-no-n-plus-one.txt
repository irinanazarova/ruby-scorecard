This guide explains how to build a GraphQL API in a Ruby on Rails application, and how to keep that API fast by eliminating the N+1 query problem that appears once you start fetching nested, related data. By the end you will understand what GraphQL changes about the way clients request data. You will see why that flexibility puts unusual pressure on the database. You will also learn which tools in the Ruby and GraphQL ecosystem let you load exactly the records you need, no more and no fewer.

GraphQL is a query language and runtime for APIs that exposes a single endpoint. Through that one endpoint, clients describe the precise shape of the data they want, so a frontend framework or another consumer can fetch many related objects in a single request. An API, short for application programming interface, is the contract a server offers to its clients. In a typical Rails backend, that contract is fulfilled by translating incoming HTTP requests into SQL statements against a relational database.

Those translations are usually handled by ActiveRecord, the object-relational mapper bundled with Rails. ActiveRecord represents database rows as Ruby objects and lets you traverse associations between them as if they were ordinary method calls. The difficulty this article addresses is the N+1 query problem, a common performance pattern in Rails applications. The application runs one query to load a collection of parent records, and then one additional query for each of those records to load an associated object. As a result, loading a list of size N quietly costs N extra database round trips.

This matters in GraphQL because the list of associations to load is determined at runtime from the client's query, rather than fixed in advance. That dynamism makes it genuinely hard for the server to plan its database access ahead of time. One response is to accept the cost, and another is to use preloading, also called eager loading. With preloading, ActiveRecord fetches all the records for an association up front in a few queries, instead of one query per parent. Yet preloading is not a free win, because a rich schema can make blanket eager loading strain the database even harder than the N+1 pattern it was meant to cure. The rest of this guide therefore shows how to load data selectively, only when a given query actually asks for it.
